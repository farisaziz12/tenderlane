Tenderlane's architecture is modelled on the tenets the TanStack libraries publish for themselves. This page takes each tenet and says what in Tenderlane backs it, with the gaps stated.

:::note
Tenderlane is an independent project. It is not affiliated with, endorsed by, or part of TanStack. The tenets are used here as a design yardstick only.
:::

## 1. Open, Independent, Technology-Agnostic

No payment provider and no framework is built into the core.

- **`@tenderlane/core` has zero runtime dependencies** and never imports a provider SDK. It holds the contracts: types, routing, catalog, middleware runner, errors, server handler.
- **PSPs exist only as adapters.** Stripe and Polar live in their own packages (`@tenderlane/stripe`, `@tenderlane/polar`) and implement the same public interfaces (`BrowserPaymentProvider`, `ServerProviderAdapter`, `Catalog`) that a third-party adapter would.
- **No privileged PSP.** Core has no default provider. Provider IDs are plain strings; a router returns one and the client looks it up among the adapters you registered.
- **Browser and server entries are separate.** `@tenderlane/stripe` does not import the `stripe` package and `@tenderlane/polar` does not import `@polar-sh/sdk`. Only the `/server` subpaths do.
- **The server handler speaks Web `Request`/`Response`**, so it is not tied to a server framework.

Gaps: there are two adapters. Adyen, Paddle, PayPal and others are not built. The known-ID types in core (`KnownProviderId`, `KnownPaymentMethodId`) list names for editor autocomplete, which is a convenience and not a dependency. `ResolvedProviderRefs` likewise types the `stripe` and `polar` keys and leaves every other provider to an index signature.

## 2. Composable, Platform-Aligned Primitives

Small pieces with one job each, joined by plain objects and web standards.

- **Router**: context in, route out. Rules are serializable JSON, so they can be stored, diffed and loaded remotely. The same router can run in the browser and on the server (the handler's `routing` option).
- **Catalog**: `{ sku, quantity }` in, priced items out. Inline, remote, custom (`defineCatalog`), Stripe-sourced and Polar-sourced implementations share one interface.
- **Headless client**: a framework-free state machine that exposes `subscribe` and `getSnapshot`, the external-store contract.
- **Thin framework binding**: `@tenderlane/react` is `useSyncExternalStore` over that client, plus `TenderlaneProvider` and `TenderlaneCheckoutForm`. It holds no payment logic.
- **Server handler**: `{ POST, resolve }`, two functions from `Request` to `Response`.

Gaps: React is the only framework binding. Vue, Solid, Svelte and others are not built; using them today means writing your own binding over `subscribe`/`getSnapshot`.

## 3. Pragmatic, Production-Grade Quality

Defaults that are safe for money, and escape hatches where the abstraction stops.

- **Price integrity by default.** The browser never sends an amount. The server resolves prices from its catalog, strips forged amounts, drops client `providerOptions`, rejects legacy `lineItems`, and validates `items`. See the [Security model](/docs/concepts/security-model).
- **Escape hatches, all explicit:**
  - `predicates` on the rules router, for conditions that cannot be expressed as data
  - middleware hooks, for observing every lifecycle step without forking the client
  - server-side `providerOptions`, for passing native options to the PSP
  - `defineCatalog`, for pricing from your own database
  - `CheckoutResult.raw`, the untouched provider response
- **Honest states.** `success` means the provider reported the payment complete. A created hosted checkout is `redirecting`, not `success`.

Gaps, stated plainly: Tenderlane is alpha. **Webhooks are not built**, and they are the only authoritative signal that a payment completed, so you must wire your PSP's webhooks yourself. Subscriptions, refunds, provider failover and devtools are not built either. APIs can change before 1.0.

## 4. Predictable, Explicit, Type-Safe Behavior

The same input gives the same result, and the compiler knows what you configured.

- **First match wins.** Rules are evaluated in order; the result records which rule matched (`ruleId`) and where it came from (`source`).
- **One state machine, immutable snapshots.** Every transition replaces the state object. One submit runs at a time. A failed submit keeps the route so it can be retried.
- **Typed errors.** Every error extends `TenderlaneError` and carries a `code` (`ROUTING_ERROR`, `PROVIDER_ERROR`, `CATALOG_ERROR`, `VALIDATION_ERROR`, ...).
- **Inference through `~types`.** Adapters and catalogs carry a phantom `'~types'` property, so `InferProviderId`, `InferPaymentMethods`, `InferCapabilities` and `InferCatalogSkus` recover literal types (`"stripe"`, not `string`) with no runtime cost. See [Type Safety](/docs/concepts/type-safety).
- **No hidden trust.** What the server accepts from the browser is listed on one page, and each relaxation (`allowLegacyLineItems`, omitting `resolveContext`) is something you opt into by name.

## What is not built

| Area | Status |
|------|--------|
| Webhook handling and verification | Not built. Use your PSP's SDK |
| Subscriptions, refunds | Not built |
| Framework bindings other than React | Not built |
| Providers other than Stripe and Polar | Not built |
| Polar embedded (iframe) checkout | Not built |
| Provider failover, ML-based routing | Not built |
| Devtools | Not built |
