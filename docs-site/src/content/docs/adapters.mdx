## Stripe

| | |
| --- | --- |
| Browser | `stripeProvider({ publishableKey, serverEndpoint })` from `@tenderlane/stripe` |
| Server | `stripeServerAdapter({ secretKey, webhookSecret? })` from `@tenderlane/stripe/server` |
| React | `StripePaymentElement` from `@tenderlane/stripe/react` |
| Peer dependencies | `stripe` (server), `@stripe/stripe-js` and `@stripe/react-stripe-js` (inline flow only) |

- `hosted` creates a Checkout Session in `payment` mode and redirects to it.
- `retrieve` reads a Checkout Session (`cs_…`) or a PaymentIntent (`pi_…`), with the payment method used. A session counts as `complete` only when its `payment_status` is `paid`; finished but unpaid (a bank debit) is `processing`.
- `inline` creates a PaymentIntent, mounts the Payment Element with its client secret, and `submit()` calls `stripe.confirmPayment`.
- A resolved item with `providerRefs.stripe.priceId` is sent as a Stripe Price; otherwise as inline `price_data` from the server's catalog.
- A PaymentIntent has one currency. A cart that mixes currencies is rejected.
- A route's `paymentMethods` become `payment_method_types`. Without them, Stripe's automatic payment methods apply.
- Webhooks are verified with Stripe's own `constructEventAsync`. Checkout Session and PaymentIntent events are interpreted; the rest arrive as `unhandled`.
- Stripe.js is loaded on demand, the first time an inline route needs it.

## Polar

| | |
| --- | --- |
| Browser | `polarProvider({ serverEndpoint })` from `@tenderlane/polar` |
| Server | `polarServerAdapter({ accessToken, server, webhookSecret? })` from `@tenderlane/polar/server` |
| Peer dependency | `@polar-sh/sdk` (server) |

- `hosted` only.
- `retrieve` reads the checkout. Only `succeeded` is `complete`; `confirmed` (payment in progress) is `processing`. Polar does not report the payment method.
- Polar sells products by id. Each item needs `providerRefs.polar.productId`, which `createPolarCatalog` supplies.
- Webhooks are verified with the Standard Webhooks scheme Polar uses, and only `checkout.updated` is interpreted. The adapter reads three fields of the payload instead of validating all of it, so a new field on Polar's side does not turn into rejected webhooks.
- One product, quantity one, per checkout. Anything else is rejected with a `CATALOG_ERROR` instead of being charged as something it is not.

## Writing an adapter

An adapter is two objects. The demo provider in the example is a complete one, written only with `@tenderlane/core/adapters`, the entry point the Stripe and Polar adapters use.

The browser half declares what the provider can do and how to submit:

The server half makes the provider calls: `handle` creates the checkout from `payload.items`, which the server's catalog already priced; the optional `retrieve` reads its state back, and the optional `verifyWebhook` checks a webhook's signature and says what it means:

<Source code={server} file="examples/react-checkout-multi-psp/app/demo-psp/server.ts" />

What the helpers do:

- `defineBrowserProvider` keeps the id as a string literal, so routing rules that name it are type-checked.
- `defineServerAdapter` types `handle`'s `action` as the union of `actions`.
- `requestProviderAction` posts one action to the app's handler in the wire format it expects, and validates the response.

For an inline flow, add `createSession(input, route)` to the browser provider, returning `{ flow, clientSecret, sessionId }`, and a component that mounts the provider's element with that secret. `packages/stripe` is the reference.

Rules for an adapter:

1. The browser entry imports no server SDK and holds no secret.
2. The server adapter reads prices only from `payload.items`.
3. If the provider cannot represent the cart, throw a `CatalogError`. Do not approximate.
4. Return `status: 'complete'` only when the provider says the payment is complete, from `handle` and from `retrieve`. Use `processing` when the customer has paid and the money has not arrived, and `open` when the customer still has something to do.
5. In `verifyWebhook`, verify against the raw body and throw `WebhookVerificationError` when it fails. Report what you cannot interpret as `unhandled`; do not throw for it.
6. Replace `{CHECKOUT_ID}` in `successUrl` with the checkout id, or with the provider's own placeholder for it.

The repository's `e2e` test runs one checkout through Stripe, Polar and a third adapter written this way, against mocked provider SDKs.
