Tenderlane routes payments in the browser. Anything that runs in the browser can be changed by whoever is using it, so the server handler treats the whole request body as untrusted input. This page states exactly where the line is.

## The rule

**The browser says what is being bought. The server decides how much it costs.**

The wire payload is `{ provider, action, payload: { items: [{ sku, quantity }], context, successUrl, cancelUrl, ... } }`. There is no amount in it. The handler runs its own `catalog.resolve()` and builds the PSP request from the result.

## What the server does not trust

| Input from the browser | What the handler does with it |
|------------------------|-------------------------------|
| `unitAmount` anywhere in the body | Stripped before anything else runs |
| `payload.providerOptions` | Always dropped |
| `payload.lineItems` (legacy shape with amounts) | Rejected with 400, unless `allowLegacyLineItems: true` and no catalog is configured |
| `payload.items` | Validated: `sku` is a non-empty string, `quantity` is an integer from 1 to `maxQuantity` (default 10 000), at most `maxItems` entries (default 100). Inherited property names such as `constructor` are not treated as SKUs |
| `payload.context` | Passed to the catalog as sent, **unless** you set `resolveContext` |
| `payload.successUrl`, `payload.cancelUrl` | `successUrl` must be a non-empty string. Both are passed to the PSP as sent, **unless** you set `allowedRedirectOrigins` |
| `payload.metadata`, `customerEmail`, `clientReferenceId`, `idempotencyKey` | Type-checked (`metadata` must be an object of string values, the others strings), then passed through. A wrong type is a 400 |
| `provider`, `action` | Must name a registered adapter and an action it supports, otherwise 400. The browser's choice of provider is accepted, **unless** you set `routing` |
| `paymentMethods` | Passed to the adapter as sent, **unless** you set `routing` |
| Malformed JSON, non-object body | 400 |

The "unless" rows are opt-in. Read the next three sections before going to production.

## What the server trusts

- Your catalog. Whatever `catalog.resolve()` returns is what gets charged (for Polar, the Polar product's own price is charged).
- Your handler configuration: `providers`, `catalog` / `catalogs`, `providerOptions`, `resolveContext`, `routing`.
- The PSP's API responses.

## `resolveContext`: do not price from a forged context

Client-side routing needs a context (country, currency, tier, experiment), and the same context is sent with the checkout. If your catalog's price depends on it, a customer can edit the request and claim the cheaper region or tier.

`resolveContext(request, clientContext)` runs on the server before the catalog and returns the context the server believes. Read the country from a geo header, the tier from the session, and so on.

```ts
import { createTenderlaneHandler } from '@tenderlane/core/server';

const handler = createTenderlaneHandler({
  providers: [/* ... */],
  catalog,
  async resolveContext(request, clientContext) {
    const session = await getSession(request);
    return {
      // Presentation choices the customer is allowed to make
      currency: clientContext.currency,
      locale: clientContext.locale,
      // Facts the server knows better
      country: request.headers.get('x-vercel-ip-country') ?? undefined,
      customer: { id: session?.userId, type: session?.accountType },
    };
  },
});
```

Without this hook the client's context reaches the catalog unchanged. That is fine when prices do not depend on it. The hook also applies to the `resolve` preview route.

## `routing`: do not let the browser pick the provider

Routing runs in the browser, and the request names the provider it chose. Without a server check, a caller can name any registered provider and so choose which adapter and which catalog handle the checkout, and which payment methods are offered.

Pass the handler the same router the client uses. The server evaluates it against the context it believes (the result of `resolveContext`, or the request's context without it), rejects a request whose `provider` is not the one the route selects with a 400, and takes the allowed payment methods from the route instead of the request body.

```ts title="lib/routing.ts"
import { createRulesRouter } from '@tenderlane/core';

// Shared by the browser and the server. Rules are plain data.
export const router = createRulesRouter({
  rules: [/* ... */],
  fallback: { provider: 'stripe', flow: 'checkout-session', paymentMethods: ['card'] },
});
```

```ts
import { router } from '@/lib/routing';

const handler = createTenderlaneHandler({
  providers: [/* ... */],
  catalog,
  routing: router,
});
```

The server can only evaluate what it is given. Send the context with the checkout (`submit({ items, context, ... })`), otherwise the server routes on an empty context and rejects any request that did not use the fallback route. Rules that use function `predicates` need the same predicates on the server.

Recommended whenever more than one provider is registered.

## Why client `providerOptions` is dropped

`CheckoutInput` has a `providerOptions` field, and provider adapters merge it into the PSP request. If the browser could set it, it could replace the line items the catalog resolved, and with them the price. So the handler always drops `providerOptions` from the request body.

Provider options are server configuration instead, keyed by provider ID:

```ts
const handler = createTenderlaneHandler({
  providers: [stripeServerAdapter({ secretKey: process.env.STRIPE_SECRET_KEY! })],
  catalog,
  providerOptions: {
    stripe: { allow_promotion_codes: true },
  },
});
```

This is an escape hatch into the PSP's native API. The values are merged into the PSP request as written, so treat them as code.

## Redirect origin allow-list

`successUrl` and `cancelUrl` come from the browser and are handed to the PSP, which sends the customer there after checkout. Without a check, a crafted request can make your checkout end on someone else's site.

```ts
const handler = createTenderlaneHandler({
  providers: [/* ... */],
  catalog,
  allowedRedirectOrigins: ['https://shop.example.com'],
});
```

When set, a request whose `successUrl` or `cancelUrl` is relative, unparseable, or on another origin is rejected with 400. When omitted, the URLs are passed through.

## Error responses

- 4xx bodies describe what the caller got wrong: `{ error: <message>, code }` with `CATALOG_ERROR` or `VALIDATION_ERROR`.
- A failed lookup against the PSP inside `createStripeCatalog` or `createPolarCatalog` (an outage, a wrong price or product ID) is a `ProviderError`, so it is a 5xx with the generic body. The ID is not echoed to the browser.
- 5xx bodies are generic: `{ error: 'Checkout request failed.', code }`. Provider and runtime error text can contain internals, so it is not sent to the browser. The original error goes to the `onError` hook. Log it there.

```ts
createTenderlaneHandler({
  providers: [/* ... */],
  catalog,
  onError: (error) => logger.error({ error }, 'checkout failed'),
});
```

## The payment outcome: webhooks, which are not built yet

Nothing the browser reports is proof of payment.

- A redirect flow ends on the client in `redirecting`. The customer pays on the PSP's page. Arriving at `successUrl` proves nothing: anyone can open that URL.
- An inline flow can end in `success`, which means Stripe.js told the browser the payment completed. A browser can be made to say anything.

The only authoritative record that a payment completed is the PSP's webhook, received and signature-verified on your server. **Tenderlane does not provide webhook handling or verification yet.** Until it does, use the PSP's own SDK in a separate route:

- Stripe: `stripe.webhooks.constructEvent(...)`, listening for `checkout.session.completed` and `payment_intent.succeeded`
- Polar: `validateEvent` from `@polar-sh/sdk/webhooks`, listening for `order.paid`

Fulfil orders, grant access and record revenue from those events only.

## What Tenderlane does not do

Be clear about what is left to you:

- **Webhooks.** See above.
- **Authentication and authorization.** The handler does not know who the caller is. Check the session yourself (before calling `handler.POST`, or inside `resolveContext`).
- **Rate limiting and CSRF protection.** Put the route behind whatever your framework provides.
- **Idempotency.** `idempotencyKey` is part of the input type, but do not rely on Tenderlane to deduplicate requests.
- **Vouching for `metadata` and `customerEmail`.** They are type-checked and then passed through to the PSP as the browser sent them.

## Production checklist

1. A catalog is configured, and `allowLegacyLineItems` is not set.
2. `resolveContext` is set if any price depends on country, tier, experiment or anything else in the context.
3. `routing` is set to the same router the client uses, and the client sends its `context` with the checkout.
4. `allowedRedirectOrigins` lists your own origins.
5. `onError` logs to somewhere you look.
6. Fulfilment is driven by PSP webhooks, verified with the PSP's SDK.
