The Tenderlane client manages checkout state through a deterministic state machine. Every state transition produces a new immutable snapshot, making the client compatible with React's `useSyncExternalStore` and similar external store patterns in other frameworks.

## Inline vs. redirect flows

The state machine fans out into two flows depending on the route's `flow` field. Inline flows (`payment-intent`) take an extra `preparing` → `prepared` hop to create a server session before submission and can end in `success` on the page. Redirect flows (`checkout-session`) go straight to `submit` and end in `redirecting`: the browser leaves for the PSP's hosted page and the payment happens there.

## States

| State | Description | `canSubmit` | Key properties |
|-------|-------------|:-----------:|----------------|
| `idle` | Only seen for an instant: before the first evaluation and inside `reset()` | `false` | No route, no provider |
| `evaluating` | Router is evaluating the context (async for the auto router) | `false` | `error` and `providerSession` cleared |
| `ready` | Route selected, provider resolved, payment methods available | `true` | `route`, `selectedProvider`, `paymentMethods` populated |
| `preparing` | Creating a provider session for inline flows (e.g., PaymentIntent) | `false` | In-progress session creation |
| `prepared` | Provider session ready, inline payment form can render | `true` | `providerSession` populated with `clientSecret` |
| `submitting` | Provider's `submit()` call is in progress | `false` | Waiting for provider response |
| `redirecting` | A hosted checkout was created and the browser is leaving for it. The payment has not happened yet | `false` | `checkoutResult` populated, with a `url` |
| `pending` | The provider accepted the submission but the payment is not complete (processing, or waiting on the customer) | `false` | `checkoutResult` populated, no `url` |
| `success` | The provider reported the payment complete | `false` | `checkoutResult.status === 'complete'` |
| `error` | Any failure during evaluation, preparation, or submission | see below | `error` populated with `TenderlaneError` |

`success` means one thing: the provider's result had `status: 'complete'`. In practice that is an inline payment confirmed on the page. A redirect flow never reaches `success` on the page that started it, because the customer pays on the provider's site.

:::caution
None of these states is proof of payment for fulfilment. `success` is what the browser was told. The only authoritative outcome is the provider's webhook, received and verified on your server. Tenderlane does not ship webhook helpers yet. See the [Security model](/docs/concepts/security-model).
:::

## Transitions

### Creating the client

`createTenderlaneClient()` evaluates the router immediately. `client.updateContext()` evaluates it again.

```ts
const client = createTenderlaneClient({
  context: { country: 'US', currency: 'usd', amount: 2500 },
  providers: [stripe],
  routing: router,
});
// For a rules router (synchronous), the state immediately reaches 'ready'
// For an auto router (async), the state passes through 'evaluating' first
```

:::tip
The rules router is **synchronous**, so the snapshot you read after `createTenderlaneClient` is already `ready` with the route resolved. This avoids SSR/hydration mismatches in React, since the server and client renders see the same initial state.
:::

### `evaluating` to `ready`

When the router returns a result, the client resolves the provider from the registered adapters, computes available payment methods, and enters `ready`. If the previously selected payment method is still offered by the new route it stays selected; otherwise the first method is selected.

If the router is asynchronous (auto router), this transition happens after the promise resolves.

### `evaluating` to `error`

If the router throws, or selects a provider that was not registered, the state transitions to `error`. No route is selected, so `canSubmit` is `false`. Fix the context with `updateContext()` or call `reset()`.

### `ready` to `submitting`

Triggered by calling `client.submit(input)`. The client calls the selected provider's `submit()` method. The input names what is being bought by SKU. It never carries an amount.

```ts
await client.submit({
  items: [{ sku: 'premium-widget', quantity: 1 }],
  successUrl: 'https://example.com/success',
  cancelUrl: 'https://example.com/cancel',
});
```

### `ready` to `preparing`

Triggered by calling `client.prepare(input)` for inline payment flows that need a server-side session (e.g., Stripe PaymentIntent). Not needed for redirect flows. `TenderlaneCheckoutForm` calls it for you.

```ts
await client.prepare({
  items: [{ sku: 'premium-widget', quantity: 1 }],
  successUrl: 'https://example.com/success',
  cancelUrl: 'https://example.com/cancel',
});
```

### `preparing` to `prepared`

After the provider's `createSession()` method returns, the `providerSession` is stored in state and the client enters `prepared`. The `providerSession` contains the `clientSecret` needed to render inline payment forms. If the context changed while the session was being created, the session is discarded: it belongs to a route that is no longer selected.

`prepare()` drops the previous provider session before it creates a new one, so a failed re-prepare cannot leave an outdated session mounted and payable.

If `createSession()` fails, the state is `error` with `canSubmit: false`. The route is kept, so `prepare()` can be called again. `TenderlaneCheckoutForm` does not retry a failing endpoint on its own: it gives the render prop a `retry()` function for a "Try again" button.

### `prepared` to `submitting`

Triggered by calling `client.submit(input)` after preparation. For the Stripe Payment Element, this confirms the PaymentIntent using the mounted Elements instance. Calling `submit()` on an inline flow that has no provider session throws a `TenderlaneError` with code `INVALID_STATE`: call `prepare()` first.

### `submitting` to `success`, `redirecting` or `pending`

The provider's `submit()` resolved with a `CheckoutResult`. The client picks the state from the result:

| Result | State | Middleware hook |
|--------|-------|-----------------|
| `status === 'complete'` | `success` | `onCheckoutSuccess` |
| any other status, with a `url` | `redirecting` | `onCheckoutPending` |
| any other status, no `url` | `pending` | `onCheckoutPending` |

`TenderlaneProvider` handles one edge of `redirecting`: if the customer comes back from the hosted page with the browser's back button and the page is restored from the back/forward cache, the provider calls `reset()` so the checkout is usable again.

### `submitting` to `error`, and retrying

The provider's `submit()` threw, for example because a card was declined, or it returned a result with status `failed` or `expired`. The error is wrapped in a `ProviderError` (unless it already is a `TenderlaneError`), stored in state, and rethrown from `submit()`. The route and the provider session are kept and `canSubmit` is `true`, so the customer can correct their details and you can call `submit()` again without re-preparing.

### One submit at a time

Only one `submit()` runs at a time. A second call while one is in flight throws a `TenderlaneError` with code `INVALID_STATE`, and so does `prepare()`. A context change or a `reset()` that arrives during a submit is deferred until the submit settles, so it cannot overwrite a completed payment or unmount an inline payment element in the middle of a confirmation. A deferred `reset()` then runs. A deferred context change re-evaluates the route only if the submit failed. Calling `submit()` or `prepare()` in a state with no selected route (`evaluating`, `submitting`, `success`, `redirecting`, `pending`) also throws `INVALID_STATE`.

### `reset()`

`client.reset()` clears the error, checkout result and provider session, then evaluates the route again for the current context. With a rules router the client is `ready` when `reset()` returns (unless a submit is in flight, in which case the reset runs when it settles). Use it to start a new checkout after `success`, `redirecting` or `pending`.

## State snapshot

Every state transition produces a new immutable object. The `getSnapshot()` method returns a stable reference until the next transition:

```ts
interface TenderlaneClientState {
  readonly status: ClientStatus;
  readonly context: TenderlaneContext;
  readonly route: SelectedPaymentRoute | null;
  readonly selectedProvider: string | null;
  readonly paymentMethods: PaymentMethodDescriptor[];
  readonly selectedPaymentMethod: string | null;
  readonly canSubmit: boolean;
  readonly error: TenderlaneError | null;
  readonly checkoutResult: CheckoutResult | null;
  readonly providerSession: ProviderSession | null;
}
```

## `useSyncExternalStore` integration

The client implements the `subscribe`/`getSnapshot` contract that React's `useSyncExternalStore` expects:

```ts
const client = createTenderlaneClient({ ... });

// In React:
const state = useSyncExternalStore(
  client.subscribe,
  client.getSnapshot,
  client.getSnapshot,  // Server snapshot (same as client for SSR)
);
```

You do not need to call `useSyncExternalStore` directly. The `useTenderlaneCheckout()` hook does this for you and returns a memoized derived state object.

## Stale evaluation handling

`updateContext()` ignores a context that is structurally equal to the current one, so passing a fresh but identical object (an inline `context={{ ... }}` prop, for example) does not re-evaluate or drop the provider session.

When `updateContext()` is called rapidly with different contexts (e.g., user types quickly in a search field), each call increments an internal version counter. When an async evaluation completes, it checks whether its version is still current. If a newer evaluation has been started, the stale result is discarded.

```ts
// These happen in rapid succession:
client.updateContext({ country: 'US', amount: 1000 });  // version 1
client.updateContext({ country: 'DE', amount: 1000 });  // version 2
client.updateContext({ country: 'CH', amount: 1000 });  // version 3

// Only version 3's result is applied. Versions 1 and 2 are discarded.
```

## Middleware integration

Middleware hooks fire at each state transition point. See [Middleware](/docs/concepts/middleware) for details.

| Transition | Middleware hook |
|-----------|---------------|
| Context changed | `onContextChange` |
| Route evaluated | `onRouteEvaluated` |
| Session created | `onSessionCreated` |
| Submit started | `onCheckoutStart` |
| Payment reported complete | `onCheckoutSuccess` |
| Hosted checkout created, or payment still processing | `onCheckoutPending` |
| Any error | `onCheckoutError` |
